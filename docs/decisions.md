- **D1 (2026-10-20) .NET 10 LTS.** Supported to Nov 2028. .NET 8 LTS ends Nov 2026; .NET 9 is STS.

- **D20 (2026-10-20) Architecture v4 approved: cost-first Stage 1 on SQS, scale path to 30,000 events/s per cell.** The owner approved all 18 decisions in `architecture.md` section 12. Two stages: Stage 1 (launch) minimizes the monthly bill; Stage 2 is a list of swaps with triggers, no rewrite. - **D21 (2026-10-20) Hybrid data layer: PostgreSQL for configuration only; SQS + DynamoDB + S3 for the data plane. No Kinesis at launch.** Supersedes D12 (transactional outbox) and the DynamoDB part of D10's reversal: Postgres stays for tenants, plans, endpoints, subscriptions, keys. Why: no relational writer can take per-event load at the target scale, and Kinesis has an hourly floor the budget does not allow. Successful deliveries leave no row; only failures and retries do.
- **D22 (2026-10-20) Delivery payload travels inline in the SQS message (KMS-encrypted), up to ~200 KB; larger via S3 pointer.** Reverses D4 (pointer-only): an extra read per delivery costs more than the bytes.
- **D23 (2026-10-20) Separate ControlPlane service (management API + portal read API), co-deployed as one tiny task.** Supersedes D8 (control plane inside Ingest).
- **D24 (2026-10-20) Accept and deliver are limited separately.** Accept: per-tenant token bucket + monthly quota (Valkey). Deliver: per-tenant delivery rate and per-endpoint rate (pacing via send slots), max backlog and max backlog age (older deliveries `Expired`), max concurrent connections per tenant and per endpoint. One delivery queue set per plan tier. Numbers are plan data (`tenancy-and-limits.md`), mostly provisional.
- **D25 (2026-10-20) Cost-first launch deployment.** One ALB, no WAF, no NAT (tasks in public subnets; fixed outbound IPs only as an Enterprise option), RDS PostgreSQL (not Aurora), one small Valkey node with local-limit fallback, Fargate Spot for the worker role, tiny tasks, ephemeral staging, local dev.
- **D26 (2026-10-20) Endpoint secrets use envelope encryption in the database with KMS**, not one Secrets Manager secret per endpoint (cost grows per endpoint).
- **D27 (2026-10-20) Customer portal lives in its own repo `webhookgateway-portal` (React + TypeScript, Cognito login).** Contracts via OpenAPI published from this repo. Success history is shown in aggregate; per-event success lookup goes through Athena (no live index).
- **D28 (2026-10-20) Monorepo + orchestrator repo.** (Recap of D14/D18/D19.) The orchestrator and the portal are separate repos; everything else is in `WebhookGateway`.
- **D29 (2026-10-20) Retry count clarified: the first attempt plus 8 retries (9 attempts) over about 24 h.** D7 said "8 attempts", but its eight backoff steps (30 s ... 10 h) sum to ~24 h only if each is followed by an attempt. Implemented in `RetryPolicy`; `architecture.md` updated.
- **D30 (2026-10-20) Identifiers are a type prefix plus a UUIDv7, not ULIDs.** Owner asked on PR #10 why a custom ULID instead of the GUID every language supports. UUIDv7 (RFC 9562) is a standard GUID that is also time-ordered, native in .NET 10 (`Guid.CreateVersion7`) and Postgres `uuid`; the prefixes and typed wrappers stay for readability and type safety. Supersedes the ULID wording in `data-plane.md`.
- **D31 (2026-10-20) Retry window depends on the plan: Basic about 24 h, Advanced about 3 days, Premium about 7 days.** Owner comment on PR #14. All plans share the first eight waits (30 s to 10 h); Advanced adds two daily waits (11 attempts) and Premium six (15 attempts). Waits over 15 minutes use the DynamoDB scheduled index, and payloads are kept in `delivery_state` (retention 30/30/90 days) so a 7-day window is covered. Supersedes the single schedule in D7/D29.
- **D32 (2026-10-21) Application logs go to CloudWatch Logs with 14-day retention; no Elasticsearch/OpenSearch at launch. Payload bodies are never logged.** Owner approved 10-14 days retention and no payload logging. CloudWatch is already in the cost model (~$15/month), needs no servers and is searchable by `eventId`/`deliveryId` with Logs Insights. Older logs are optional via S3 export (Athena). Elasticsearch/OpenSearch (fixed ~$100+/month) is a Stage 2 swap if search becomes too slow or costly. For debugging a payload, look it up in the S3 archive by `eventId`. Separate from the tenant-facing S3 result logs.
- **D33 (2026-10-21) Archive objects are gzip JSON Lines, pointer is `s3://bucket/key#line`.** `data-plane.md` said zstd; gzip is in the .NET base library (no extra dependency) and compresses well enough at our volumes. Revisit zstd/Parquet with the Athena work. Reading one payload streams the object up to its line, which is fine for batch-sized objects.
- **D34 (2026-10-21) DynamoDB adapters: one `UpdateItem ADD` per rollup row; fixed 30-day `delivery_state` TTL for now; FNV-1a for the scheduler's due buckets.** Why: atomic `ADD` is what lets many workers add to the same minute row without coordination, and DynamoDB batch writes cannot do `ADD`; row count follows active endpoint pairs, not event rate (`data-plane.md` section 4), so one call per row is cheap. TTL is a single option until the plan lookup exists (target 30/30/90 days by plan, `tenancy-and-limits.md`); the per-plan value is a small follow-up when the Dispatcher knows the tier at write time. 16 due buckets and a hand-rolled stable hash avoid a hot scheduler partition and an extra package (`string.GetHashCode` differs per process). Rollup rows carry their own TTL (7 days for 1-minute rows).
- **D35 (2026-10-21) Load and performance tests run in the test environment with the load generator and mock subscribers as on-demand ECS tasks; the output is a measured capacity table (`capacity.md`).** Owner asked for end-to-end load tests with seeded tenants, optionally from a laptop or from ECS, and for metrics that say how many minimum resources production needs per workload. Why ECS for the real runs: a laptop cannot generate 30k events/s and home-network latency would pollute the numbers; the same container images run locally for smoke only (no capacity numbers from local). Open-loop generation avoids coordinated omission. Tasks scale to zero when idle so the test environment stays near its minimum bill. Capacity assumptions in `architecture.md`/`cost-model.md` are replaced by measured values (LT-9), and autoscaling/alarm settings come from them (LT-10). Plan: `load-testing.md`.
- **D36 (2026-10-21) Dispatcher consumes one receive loop per plan tier, with bounded concurrency and per-message acknowledge.** Why: tier queues exist so higher plans are not slowed by lower ones (D24), so each tier gets its own loop and its own concurrency limit (default 100 in flight). Sending is async I/O, so concurrency is bounded by connections rather than threads. A message is deleted only after `DeliveryProcessor` finished; an exception leaves it for SQS redelivery (safe because processing is idempotent). Unreadable messages are logged (id only, never the body), skipped and end up in the DLQ after 5 receives. `IDeliveryProcessor` was extracted so the consumer is testable without the full dependency graph. The concurrency number is a starting value to replace with load-test results (P3-4).
- **D37 (2026-10-21) Ports (interfaces and their records) live in `src/Abstractions`, namespaces unchanged.** Why: the AWS adapters (`src/Aws`) implement the ports, and the hosts must reference `src/Aws` to wire them; while the ports sat inside the service projects that was a circular reference (Aws -> Ingest/FanOut/Dispatcher -> Aws). A neutral project holding only interfaces and plain records removes the cycle, and any other broker or store (a RabbitMQ project, Postgres store) would plug in the same way. Namespaces were kept (`WebhookGateway.Ingest.Publishing`, ...), so no consumer or test changed. Moved: `IEventPublisher`, `IEventSource`, `IDeliveryPublisher`, `IEventArchive`, `IPayloadResolver`, `IRetryPublisher`, `IDeliveryStateStore`, `DeliveryStateRecord`, `IDeliveryProcessor`, `DeliveryAction`, `IDeliverySource`.
- **D38 (2026-10-21) Every log line carries a `component` field (Ingest, FanOut, Dispatcher, ControlPlane); we use our own flat JSON console formatter instead of the built-in one.** Owner asked for it so the failing part is obvious when troubleshooting. Why a formatter and not a scope: scopes only apply inside the code that opens them, so lines from hosting and libraries would miss the field; a formatter stamps every line. It also flattens the structured fields (`tenantId`, `deliveryId`, ...) to the top level, which is what CloudWatch Logs Insights filters on, and removes the nested `State`/`Scopes` noise noted on the logging PR. `category` still names the class. Replaces the built-in `AddJsonConsole` from L-2.
- **D39 (2026-10-21) One switch, `Backend:Mode` = `InMemory` (default) or `Aws`, selects the adapters; each role registers only what it needs.** Why: the same binaries must run in unit tests (no AWS), on a laptop against Moto, and in production, and a single explicit flag is easy to audit in the task definition. Production sets only the mode (the task role supplies credentials); `Aws:ServiceUrl` is set only for emulators and also switches to static dev credentials, so production can never accidentally use them. The Dispatcher queue consumer starts only in Aws mode because it needs the queues, the archive and `delivery_state`. Tests set the mode with `UseSetting`, since `Program.cs` reads it before late test configuration is applied. Known gap: subscriptions (Fan-out) and endpoints (Dispatcher) are still in-memory until the config database stores exist (P1-2 migrations, P2-1), so Aws mode moves events end to end only for tenants that have routing.
- **D40 (2026-10-21) Long retry waits: the scheduler publishes first, then flips the row; the tier is stored on the row.** Waits over 15 minutes cannot use SQS `DelaySeconds`, so they sit in `delivery_state` as `Scheduled` and a poller (every 10 s, up to 200 per poll) puts them back on the tier queue when due. Order is publish, then write `RetryScheduled` (which drops the row from the due index): the opposite order could lose a delivery if the process died between the two steps, while this order can at worst produce a duplicate, which the Dispatcher already tolerates (stable delivery id, at-least-once). `Tier` was added to `DeliveryStateRecord` because the scheduler has no other way to know which queue a tenant's delivery belongs to (the plan lookup arrives with the config database). Rows written before this change default to the Basic queue. The poll interval and batch size are starting values for load testing (LT items).
- **D41 (2026-10-21) Rollups: counted where the work happens (Fan-out counts `created`, Dispatcher counts attempts), flushed every 10 s, failed rows carried to the next flush, one final flush on shutdown.** Why: each service owns its own in-memory accumulator, and DynamoDB `ADD` lets both write the same minute row without coordination (D34). The writer reports which rows it could not store instead of throwing half-way, and those rows are put back in their final form (a separate carry list), so neither a short DynamoDB outage nor a partial failure loses counts or counts the tenant-wide row twice. A hard crash still loses at most one flush interval of counters; the S3 result logs stay the audit truth (`data-plane.md` section 6). Queue wait is measured from the message's `notBefore` (when it was due), response time from the sender. `Restore` was added to `RollupAccumulator`; `IRollupWriter` lives in `src/Abstractions` (D37).
- **D42 (2026-10-21) Accept-side limits in Valkey with automatic fallback; monthly quota is counted always but enforced only by a switch (default off).** What: a shared token bucket (one atomic Lua script, server clock), idempotency keys (`SET NX` for the plan's window), and a monthly counter (`INCR`, key expires after 40 days), in a new `src/Valkey` project; Ingest wraps each in a decorator that falls back when Valkey is unreachable (local limiter; idempotency and quota checks skipped, each failure logged as a warning), so Valkey never takes ingestion down (`architecture.md` section 5, degraded mode). Why quota enforcement is off: the plan quotas are still `TBD` (placeholders 1M / 20M / 100M, a pricing decision that is the owner's), and rejecting real customers at a made-up number would be worse than counting. Counting stays on so billing data exists from day one; `Ingest:Quota:Enforce=true` turns the 429 on once the numbers are set. Order in the endpoint: count, then claim the idempotency key, then publish; a duplicate, an over-quota event or a failed publish takes the count back and a failed publish also releases the key, so a retry is never answered with an event that was never stored. Not done yet (deliberately): reserving tokens in chunks of about 20 to cut Valkey calls (an optimization for high volume; add after load tests, LT items), and the once-a-minute flush of the counter to PostgreSQL `usage_monthly` (needs the config database). Degraded mode uses the full plan rate per task instead of `rate / tasks` because the task count is not known to the task; it can over-admit by the number of tasks during an outage. Ports for these (`IRateLimiter`, `IIdempotencyStore`, `IQuotaCounter`, `PlanLimits`) moved to `src/Abstractions` for the same cycle reason as D37.
- **D43 (2026-10-21) Config database implementation choices (the `(review)` items in `database.md`): plain Npgsql, UUID columns without prefix, no row-level security at launch, password from Secrets Manager first, UUIDv7 generated by the application.** Why: (1) *Npgsql for the read-path stores (Ingest, Fan-out, Dispatcher), no Dapper:* those are a few small read-only queries on the request path, so a mapper saves no code and we want exact SQL without tracking overhead. *EF Core is allowed in the ControlPlane* for CRUD (many tables, validation, transactions, off the hot path) mapped onto the existing tables; the schema stays in plain SQL migrations and EF must not generate it (`database.md`). Owner asked why not EF (2026-10-21); this is the answer. (2) *UUID without the `ten_`/`ep_` prefix in the column:* native `uuid` is smaller and indexes better; the application adds the prefix (`ConfigIds`), as D30 intended. (3) *No RLS yet:* ControlPlane is the only writer and every read filters on `tenant_id` in code that is covered by tests; RLS needs per-request session settings through the connection pool, which is risk without a second tenant-facing writer. Revisit when the portal reads the database directly (P2-2). (4) *Password in Secrets Manager first, IAM auth later:* IAM auth adds token refresh and pool handling; not needed to launch. (5) *UUIDv7 in the application (`Guid.CreateVersion7`)*, because PostgreSQL 16 has no native `uuidv7()`. (6) *Seed plans are a migration:* plans are data; the numbers other than the accept rates are placeholders and change with a new migration or the ControlPlane. (7) *Migrations:* plain SQL, one transaction each, checksum stored so an edited applied file is an error (forward-only), advisory lock against concurrent runners, run by the deploy job and `dev-up.sh`, never by a service at startup. (8) *Cache:* 30 s positive TTL as specified, 5 s for unknown keys/tenants so bad credentials cannot hammer the database; `last_used_at` on `api_keys` is not updated on the hot path (a write per request) and will be batched later. Not in this change: the endpoint store (needs envelope encryption with KMS for secrets, next to the ControlPlane), the `usage_monthly` flusher, config-change invalidation.
- **D44 (2026-10-21) `database.md` approved as Final v1.** Owner reviewed the schema, seed plans and D43 on PR #34 and approved ("looks good go ahead"). Plan numbers other than the accept rates remain placeholders and can be changed with a new migration.
- **D45 (2026-10-21) Endpoint signing secrets: AES-256-GCM with a per-secret KMS data key; the Dispatcher decrypts once per cache period.** What: `KmsSecretProtector` asks KMS for a fresh data key per secret (`GenerateDataKey`), encrypts the secret with AES-GCM, and stores the KMS-encrypted key blob together with the ciphertext in `endpoints.secret_ciphertext`; `secret_kms_key_id` records the master key. Why envelope encryption (D26): one Secrets Manager secret per endpoint would cost per endpoint per month, and calling KMS to encrypt the secret directly is limited to 4 KB and ties every decrypt to one key version; envelope keeps the database holding only ciphertext. Why the Dispatcher caches: decrypting is one KMS call, so `PostgresEndpointStore` keeps the decrypted target for the 30 s cache TTL (a few KMS calls per endpoint per minute at worst, in the cents per month range; the load test should confirm). A `LocalSecretProtector` (key from `Secrets:LocalKey`) exists for development and tests only; with neither `Secrets:KmsKeyId` nor `Secrets:LocalKey` configured the service refuses to start rather than store secrets unprotected. GCM authenticates the data, so a tampered row is rejected. The ports and `SigningSecret` moved to `src/Abstractions` (same cycle reason as D37). One secret per endpoint for now; rotation with two active secrets (the sender already supports it) needs a second column or table, to be added with the ControlPlane rotation endpoint.
- **D46 (2026-10-21) ControlPlane v1 is an operator-only admin API behind one admin key, built with EF Core on the existing tables.** Why operator-only: tenants are created by an operator in v1 (`tenancy-and-limits.md`), and the customer login (Cognito, P2-3) and portal API come later; building self-service now would delay launch. Why a single key in a header: simplest thing that is safe over HTTPS, compared in constant time on hashes, disabled (503) when not configured so an unconfigured deployment can never be open; the key lives in Secrets Manager/environment, never in the repo. It is intended for a handful of operator actions, and moving to Cognito groups later does not change the routes. Why EF Core here (D43): this is CRUD over five tables with checks and transactions, off the hot path; the context maps only the columns it uses and never generates schema. Secrets and API keys are returned exactly once. Business rules enforced in the API: plan must exist, endpoint cap per plan, a plan change below the endpoint count is refused, URLs pass the same SSRF validator the Dispatcher uses. Every state change is logged with tenant and object ids, never with keys or secrets. Cache invalidation is not built: changes show up within the 30 s cache TTL, which is acceptable for operator-driven changes; add explicit invalidation if a faster suspend is needed. API/secret *rotation* of endpoint secrets is not included (D45 note).
- **D47 (2026-10-21) The developer site, docs and purchase flow are Phase 5 (S-1..S-15), built last; we will not claim "end-to-end encrypted" unless it is built.** Owner asked for a docs website with menus, interactive tools and sample code in many languages, plus the plan purchase flow, and for customers to feel confident about encryption. Why last: it describes behavior that must be finished and stable, and sample code is only trustworthy if CI runs it against the real system (S-5, S-12). Why a separate repo: same reasoning as the portal (D27), different release rhythm, and the OpenAPI document published from this repo keeps the reference in step with the code. Why the careful encryption wording: the platform has to read events to route and deliver them, so the accurate claim is TLS in transit, encryption at rest everywhere and signed deliveries; overstating it would damage trust and may be misleading. Real end-to-end encryption (customer-held keys) is offered as a possible later feature (S-14) because it trades away replay and inspection. Payment provider and prices are owner decisions (Razorpay or Stripe, plan numbers) needed before S-9.
