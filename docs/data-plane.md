# Data plane

Status: **APPROVED design** (2026-10-20, D20-D22); message shapes finalize when implemented. Describes the high-volume path from `architecture.md` v4 (SQS-based, cost-first). Names and shapes are proposals; `contracts.md` is updated after approval.

PostgreSQL holds configuration only (`tenancy-and-limits.md` section 6). Everything per-event lives here.

## 1. Stores at a glance

| Store | What | Why this store | Cost behaviour |
|---|---|---|---|
| SQS `events` (+ DLQ) | Accepted events awaiting fan-out | Durable, multi-AZ, absorbs bursts, no hourly floor | Per request |
| SQS `deliveries-{tier}` (+ DLQ) | One message per delivery, payload inline, send slot as `DelaySeconds` | Per-message retry, delay, DLQ | Per request |
| DynamoDB `delivery_state` | Deliveries that failed, are retrying, parked or scheduled for later than 15 min | Key-value at any scale, queryable by tenant, endpoint, status | On-demand, about 2% of deliveries |
| DynamoDB `rollups` | Per tenant, endpoint, minute counters and latency histograms | Cheap range reads for dashboards | On-demand, depends on active endpoints |
| S3 `archive/` | Event payload batches | Replay and retention at object-store cost | Thousands of events per PUT |
| S3 `results/` | Batched result logs (gzip JSON Lines, Parquet later) | Athena search and export | One PUT per task per minute |
| Valkey (one node) | Rate buckets, counters, idempotency keys, circuit state, pacing slots, connection permit leases | Sub-millisecond atomic operations | Fixed, small |
| RDS PostgreSQL | Tenant config | Relational, low volume | Fixed, small |

There is **no Kinesis** in this design. Replay comes from the S3 archive and from `delivery_state`.

## 2. Identifiers

A type prefix plus a **UUIDv7** (RFC 9562, a standard GUID whose first 48 bits are the creation time, so ids sort by creation time), generated by the service that creates them and globally unique without coordination: `evt_`, `ten_`, `ep_` followed by the hyphenated UUID, for example `evt_0192f3a4-7c1b-7d2e-9a10-3b5c8e7f1a22`. A delivery id is derived from the event and endpoint UUIDs (`dlv_{event:N}_{endpoint:N}`), so it is stable across retries and across a repeated fan-out batch (this is the `webhook-id` the subscriber sees). Decided on PR #10 review (D30).

## 3. Messages

**Event message (SQS `events`)**
```json
{ "schemaVersion": 1, "eventId": "evt_...", "tenantId": "ten_...", "type": "order.created",
  "occurredAt": "2026-10-20T10:00:00Z", "receivedAt": "2026-10-20T10:00:00.120Z",
  "idempotencyKey": null, "payload": { } }
```

**DeliveryMessage (SQS `deliveries-{tier}`)**: payload inline up to about 200 KB; larger payloads use `payloadRef` into the S3 archive. Pacing uses the SQS `DelaySeconds` attribute (maximum 15 minutes).
```json
{ "schemaVersion": 1, "tenantId": "ten_...", "eventId": "evt_...", "deliveryId": "dlv_...",
  "endpointId": "ep_...", "eventType": "order.created", "occurredAt": "2026-10-20T10:00:00Z", "attempt": 1,
  "createdAt": "...", "notBefore": "...", "payload": { }, "payloadRef": null }
```

**Result log line (S3 `results/`)**: one per attempt, written in batches by Dispatcher.
```json
{ "tenantId": "ten_...", "endpointId": "ep_...", "deliveryId": "dlv_...", "eventId": "evt_...",
  "attempt": 1, "outcome": "Succeeded|Retry|Failed|Exhausted", "statusCode": 200,
  "queueWaitMs": 120, "responseMs": 85, "error": null, "ts": "..." }
```
No payload bodies and no secrets in result logs.

## 4. DynamoDB tables

**`delivery_state`** (only non-success deliveries)

| Key | Value |
|---|---|
| PK `tenantId#deliveryId` | status (`RetryScheduled`, `Parked`, `Scheduled`, `Failed`, `Exhausted`, `Expired`), attempt, nextAttemptAt, lastStatusCode, lastError, endpointId, eventId, payload (inline or `payloadRef`), createdAt, ttl |
| GSI1 `tenantId#status` / `updatedAt` | portal: failures list |
| GSI2 `tenantId#endpointId` / `updatedAt` | portal: per-endpoint view |
| GSI3 `dueBucket` / `nextAttemptAt` | retry scheduler (sharded buckets to avoid a hot partition) |

TTL deletes rows after the plan's retention. Payload limit is 256 KB, below the 400 KB item limit.

**`rollups`**

| Key | Value |
|---|---|
| PK `tenantId#endpointId` / SK `resolution#minute` | created, succeeded, failed, retried, timeouts, latency histogram buckets (for p50/p95/p99), queue-wait histogram, pending gauge, connection-seconds |

Workers keep counters in memory per key and flush every 10 seconds with atomic `ADD`, so the write rate depends on active (tenant, endpoint) pairs, not on event rate. A scheduled compaction job writes hourly and daily rows. Tenant-wide rows use endpoint `*`. Histograms are additive, so many workers can write the same key.

## 5. S3 layout

- `archive/region=<r>/date=<d>/hour=<h>/<workerId>-<seq>.jsonl.gz`: event batches written by Fan-out (gzip JSON Lines, one `EventMessage` per line), encrypted with KMS. One PUT per batch. A `payloadRef` is `s3://<bucket>/<key>#<zero-based line>` (D33).
- `results/tenant=<id>/date=<d>/<workerId>-<minute>.jsonl.gz`: result logs; the Athena workgroup is queried only through ControlPlane with the tenant id fixed server-side.
- Lifecycle rules enforce retention per prefix; tenant deletion removes by prefix.

## 6. Consistency and failure rules

- **At-least-once** end to end; receivers dedupe on `webhook-id`. Fan-out is idempotent per `(eventId, endpointId)`: a redelivered `events` message regenerates the same `deliveryId`s, and Dispatcher treats a `deliveryId` already finished in `delivery_state` as done.
- **Fan-out deletes an `events` message only after** the archive segment is written and every delivery message of that event is enqueued. A crash in between means the event is processed again (duplicates are harmless).
- **Crash after send, before counting:** SQS redelivers the message and it is sent again (allowed by at-least-once). Counters can over-count by the in-flight amount of a crashed worker; the S3 result logs are the audit truth.
- **Replay:** portal replay re-enqueues a delivery from `delivery_state`, or from the S3 archive for older events, with `attempt` reset and a new `replayId`.
- **Poison messages:** after `maxReceive` the message moves to the DLQ, an alarm fires, and a `delivery_state` row with status `Failed` is written so the tenant sees it.
- **Queue limits to remember:** SQS standard allows about 120,000 in-flight messages per queue, 256 KB per message, 14 days retention, 15 minutes maximum delay. The in-flight limit is why delivery queues are sharded by endpoint hash at higher volume (`architecture.md` section 10).

## 7. Retention

SQS: set to the 14-day maximum on all queues as an incident buffer (a delivery older than the plan's max backlog age is expired, not sent). `delivery_state`: plan retention via TTL. Archive and result logs: plan retention via S3 lifecycle. Rollups: 1-minute rows 7 d, hourly 90 d, daily 13 months.
