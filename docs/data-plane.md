# Data plane

Status: **PROPOSAL v1, for owner review** (2026-10-20). Describes the high-volume path from `architecture.md` v3. Names and shapes are proposals; `contracts.md` is updated after approval.

PostgreSQL holds configuration only (`tenancy-and-limits.md` section 6). Everything per-event lives here.

## 1. Stores at a glance

| Store | What | Why this store | Volume at 30,000 events/s |
|---|---|---|---|
| Kinesis `events` | Accepted events awaiting fan-out | Durable multi-AZ log, replayable, absorbs bursts | ~60 MB/s in |
| SQS `deliveries-{tier}` (+ DLQ) | One message per delivery, payload inline | Per-message retry, delay, DLQ | ~90,000 msg/s |
| Kinesis `results` | One record per attempt outcome | Feeds rollups and history without a database | ~90,000 rec/s |
| DynamoDB `delivery_state` | Deliveries that failed, are retrying, parked or scheduled | Key-value at any scale, queryable by tenant/endpoint/status | ~2% of deliveries |
| DynamoDB `rollups` | Per tenant, endpoint, minute counters and latency histograms | Cheap range reads for dashboards | ~3,000 writes/s |
| S3 `archive/` | Event payload batches | Replay and retention at object-store cost | Thousands of events per object |
| S3 `results/` (Parquet) | Outcome history | Athena search and export | via Firehose |
| Valkey | Rate buckets, counters, idempotency keys, circuit state, pacing slots, connection permit leases | Sub-millisecond atomic ops | ~90,000 ops/s |
| Aurora PostgreSQL | Tenant config | Relational, low volume | idle |

## 2. Identifiers

Prefixed ULIDs, generated by the service that creates them, globally unique without coordination: `evt_`, `dlv_`, `ten_`, `ep_`. A delivery id is `dlv_` + event ULID + endpoint suffix so it is derivable and stable across retries (this is the `webhook-id` the subscriber sees).

## 3. Messages

**Event record (Kinesis `events`)** partition key = `eventId` (even spread; no ordering promise).
```json
{ "schemaVersion": 1, "eventId": "evt_...", "tenantId": "ten_...", "type": "order.created",
  "occurredAt": "2026-10-20T10:00:00Z", "receivedAt": "2026-10-20T10:00:00.120Z",
  "idempotencyKey": null, "payload": { } }
```

**DeliveryMessage (SQS)** payload inline (up to ~200 KB; larger payloads use `payloadRef` to the S3 archive).
```json
{ "schemaVersion": 1, "tenantId": "ten_...", "eventId": "evt_...", "deliveryId": "dlv_...",
  "endpointId": "ep_...", "eventType": "order.created", "attempt": 1,
  "createdAt": "...", "notBefore": "...", "payload": { }, "payloadRef": null }
```

**Result record (Kinesis `results`)** one per attempt, and one per delivery created.
```json
{ "tenantId": "ten_...", "endpointId": "ep_...", "deliveryId": "dlv_...", "eventId": "evt_...",
  "kind": "created|attempt", "attempt": 1, "outcome": "Succeeded|Retry|Failed|Exhausted",
  "statusCode": 200, "queueWaitMs": 120, "responseMs": 85, "error": null, "ts": "..." }
```
No payload bodies and no secrets in result records.

## 4. DynamoDB tables

**`delivery_state`** (only non-success deliveries)

| Key | Value |
|---|---|
| PK `tenantId#deliveryId` | status (`RetryScheduled`, `Parked`, `Scheduled`, `Failed`, `Exhausted`), attempt, nextAttemptAt, lastStatusCode, lastError, endpointId, eventId, payload (inline or `payloadRef`), createdAt, ttl |
| GSI1 `tenantId#status` / `updatedAt` | portal: failures list |
| GSI2 `tenantId#endpointId` / `updatedAt` | portal: per-endpoint view |
| GSI3 `dueBucket` / `nextAttemptAt` | retry scheduler (sharded buckets to avoid a hot partition) |

TTL deletes rows after the plan's retention. Payloads over 400 KB do not occur (limit 256 KB).

**`rollups`**

| Key | Value |
|---|---|
| PK `tenantId#endpointId` / SK `resolution#minute` | created, succeeded, failed, retried, timeouts, latency histogram buckets (for p50/p95/p99), queueWait histogram, pending gauge |

Aggregators buffer in memory for 10 s per key and write with atomic `ADD`, so write rate depends on active (tenant, endpoint) pairs, not on event rate. A compaction job writes hourly and daily rows so long ranges stay cheap. Tenant-wide rows use endpoint `*`.

## 5. S3 layout

- `archive/region=<r>/date=<d>/hour=<h>/shard=<s>/<firstSeq>-<lastSeq>.jsonl.zst`: event batches written by Fan-out, encrypted with KMS. One PUT per thousands of events.
- `results/tenant=<id>/date=<d>/...parquet`: outcomes via Firehose; the Athena workgroup per environment, queried only through ControlPlane with the tenant id fixed server-side.
- Lifecycle rules enforce retention per prefix; tenant deletion removes by prefix.

## 6. Consistency and failure rules

- **At-least-once** end to end; receivers dedupe on `webhook-id`. Fan-out is idempotent per `(eventId, endpointId)`: a repeated Kinesis batch regenerates the same `deliveryId`s, and Dispatcher treats a `deliveryId` already marked finished in `delivery_state` as done.
- **Fan-out checkpoints** the Kinesis sequence only after all messages in the batch are enqueued and the archive segment is written.
- **Crash after send, before result record:** the message is redelivered by SQS and sent again (duplicate, allowed by at-least-once).
- **Replay:** portal replay re-enqueues a delivery from `delivery_state` (or from the S3 archive for older events) with `attempt` reset and a new `replayId`.
- **Poison messages:** after `maxReceive` the message moves to the DLQ, an alarm fires, and a `delivery_state` row is written with status `Failed` so the tenant sees it.
- **Cell loss:** Kinesis, SQS and DynamoDB are multi-AZ; the 24 h Kinesis retention and S3 archive allow rebuilding the delivery queues after a bad deploy.

## 7. Retention

Kinesis `events` and `results`: 24 h (extendable to 7 d during incidents). `delivery_state`: plan retention via TTL. Archive and results: plan retention via S3 lifecycle. Rollups: 1-minute rows 7 d, hourly 90 d, daily 13 months.
